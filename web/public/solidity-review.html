What the Solidity review checks

The profile works through the contracts in a fixed order before it writes anything.

  1. Entry points

    Every external or public function that changes state: who can call it, whether it carries a reentrancy guard, and whether value moves in or out.

  2. Sibling diff

    Each function next to the others that do the same work. A modifier, pause check or checkpoint that one sibling has and another lacks is a finding.

  3. Invariants

    Conservation, ratio, ordering and bounds. For each one, every line that writes the variables involved. One write site that skips the update breaks it.

  4. Value flow and rounding

    Which way every division rounds and who gains, the first deposit into an empty pool, and direct transfers that move a price or a share ratio.

  5. Checkpoints and external calls

    Accumulators updated before a balance changes. State that is stale at the moment of each call, token transfer, hook or callback.

  6. Signatures, oracles, upgrades

    Nonce, deadline and chain id inside the signed data. Stale or movable prices. Initialisers callable twice and privileged setters left open.

What to paste in

The review judges the files you supply and names what it could not see.

  • The contracts in scope

    One file or a small set. Import them from GitHub at a pinned commit to keep line numbers exact.

  • Interfaces, libraries and tokens they callOptional

    A control that lives in an unsupplied file is reported as depending on that file.

  • ContextOptional

    The target, the commit, how the tokens behave, and whether privileged roles are in scope.

Up to 50 files, 120 KB per file, 240 KB and 20,000 lines in total. Paste, drop files, or import a repository, pull request or commit from GitHub at a pinned commit.

What comes back

One review in a fixed format, built to be checked against the source.

  • A verdict and a one-sentence headline.
  • A finding card per issue: severity, basis, location, impact and the path with concrete values.
  • The strongest counterargument to each finding, marked resolved or open.
  • The evidence gap: the one artefact still missing.
  • A fix and a test for each finding.
  • Entry points and Invariants tables, then Hardening and Checked-and-safe lists.
  • A packet with the SHA-256 manifest of every file reviewed.

Questions

Which model runs the review?

The one you choose, on your own key: OpenRouter, Anthropic, OpenAI, Google Gemini, xAI, DeepSeek, Mistral or Groq. Or copy the prompt into ChatGPT or Claude and paste the answer back. From a coding agent, prepare_review hands the same request to the agent’s own model over MCP.

Does it work for a bounty and for my own code?

Yes. In bounty mode the verdict is submit, rewrite-then-submit, prove-first, hold-duplicate or drop. In own-code mode it is fix-before-deploy or no-blocking-issues.

How does it treat admin-only bugs?

A bug that needs the owner or an admin to act against users is listed under Hardening. Say in Context that privileged roles are in scope and it is reported as a finding.

Where do my files go?

To the model provider you choose, through our server, for that one request. Bounty Operator does not store your files, prompts, keys or results. With an exported prompt they go from your browser to the chat app you paste into. The packet you download carries a SHA-256 manifest of every file reviewed.
