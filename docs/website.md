# Web app

The source of [bountyoperator.com](https://bountyoperator.com/): a Cloudflare
Worker, a D1 database and a static front end. There is no framework, no bundler
and no runtime build step. This page covers the layout, local development, the
tests and the deploy command.

## Layout

```text
web/
  site/                  page sources (not deployed)
    layout.mjs           page shell: head, header, footer, JSON-LD
    components.mjs       shared HTML helpers
    fragments/           workbench and account dialog markup
    pages/**/*.mjs       one module per page: path, title, description, body
  public/                deployed as-is
    *.html               generated by scripts/build-site.mjs; never hand-edited
    css/                 base.css, home.css, workbench.css and per-page sheets
    theme.js             page bootstrap, the only classic script
    field.mjs            the moving field behind every page head
    review-core.mjs      input checks, manifest, request assembly, prompt export
    providers.mjs        provider endpoints, request shapes and error messages
    profiles.mjs         the three core profiles, the name and output sections of every hosted one, the Gauntlet order
    parse.mjs            review parser, reference checker
    evidence.mjs         context block and the downloadable packet
    github.mjs           commit-pinned GitHub import
    app/*.mjs            browser app
    tools/*.mjs          the free tools
    templates/           report templates and the Foundry scaffold
  src/                   the Worker (TypeScript)
  migrations/            D1 schema
  tests/                 node:test suites
scripts/build-site.mjs       static page generator
scripts/build-mcp.mjs        packs the MCP download served under /dl/
scripts/select-profiles.mjs  chooses where the Worker gets the hosted profiles from
scripts/deploy.mjs           the production deploy and the gates in front of it
scripts/verify-live.mjs      checks a running site from the outside
scripts/lighthouse.mjs       runs Lighthouse on the pages of a running site
mcp/                     the bounty-operator-mcp package
```

The engine modules in `web/public/` are plain ES modules. The browser, the
Worker and the MCP server all import the same files, so a review prepared in
any of them produces the same request and the same SHA-256 manifest.

## Core and hosted profiles

Three profiles are core: `general`, `solidity` and `report`. Their method is in
`web/public/profiles.mjs`, and they run anywhere: hosted, as an exported prompt,
or over MCP on an agent's own model.

Every other profile is hosted. `profiles.mjs` carries its name, description,
inputs and output section titles, with `hosted: true` and no method. Its method
is added by the Worker when the review runs. The method the hosted service uses
is not in this repository. A checkout runs the hosted profiles on the short
instructions in `web/src/operator-profiles.stub.mjs`.

`scripts/select-profiles.mjs` writes `web/src/operator-profiles.generated.mjs`,
the one module the Worker imports hosted profiles through. `npm test`,
`npm run dev` and `npm run types` run it first. `GET /api/health` says which
source a running Worker was built from: `"profiles": "community"` for the stub,
`"profiles": "hosted"` for the hosted service.

What each outlet does with a hosted profile:

| Outlet | Result |
| --- | --- |
| `GET /api/profiles`, MCP `list_profiles` | Name, description, inputs and `hosted: true`. No method. |
| `POST /api/review`, `POST /api/client/review`, MCP `run_review` | The review. The method goes to the provider in the system message and nowhere else. |
| MCP `prepare_review`, remote and local | Refused with `hosted_profile` before any file is read. |
| Prompt preview in the workbench | The request that leaves the tab: focus, context and numbered files. No copy, no download. |
| Prompt export and paste-back | Offered for the three core profiles only. |
| The MCP download | Core profiles only. |

The Worker also reads the answer to a hosted profile on its way back
(`web/src/guard.mjs`). An answer that repeats the method is stopped and the
request ends with `output_withheld`, as a 502 or as a server-sent `error`
event, and counts as a review. The guard compares against the method text
only: a model that returns the output template unfilled has written a poor
answer, and that answer is delivered.

`scripts/leak-audit.mjs` compares every file git would publish, everything
under `web/public` and the MCP download with the hosted method, and fails on a
match. It needs the module that holds the hosted method, so in a checkout
without it the script prints a notice and exits 0.

## How a review runs

1. `checkInputs` scans the selected files and the instructions for secrets,
   private report links and credential files. Blocking findings stop the request.
   Email and IP matches are warnings the user acknowledges.
2. `prepareRequest` builds the manifest (label, bytes, lines, SHA-256 per file) and
   the request: the focus, the context and every file with line numbers, so the
   model can cite `input-N/<name>:line`. It works for every profile and is what
   the preview of a hosted profile shows. `prepareReview` adds the system message
   with the method. In the browser and in the MCP download it does that for the
   core profiles only.
3. A hosted run posts the files, the focus, the context, the provider, the model
   and the key to `POST /api/review`. The Worker validates all of it again, runs
   `prepareReview` with the method of the profile, reserves quota in D1, calls
   the provider from `providers.mjs` and returns JSON or a `text/event-stream`.
4. `parseReview` turns the answer into a verdict, findings and sections.
   `checkRefs` marks any reference that points outside the supplied files.
5. `reviewPacket` writes the packet: verdict, context, manifest and the review.

Limits: 50 files, 120 KB per file, 240 KB and 20,000 lines of text per review,
16,000 characters of instructions. Provider calls use one fixed endpoint per provider, refuse
redirects, time out after 180 seconds and read at most 2 MB.

Source files, instructions, provider keys and review text are held in memory for
the length of the request. D1 stores accounts, passkey public keys, hashed
session, recovery and connection tokens, quota records, review metadata (time,
status, profile, channel) and Stripe references.

## Rules for front-end code

- The Worker sets one Content Security Policy for every response:
  `script-src 'self'; style-src 'self'`. No inline script and no inline style.
- No `innerHTML`, `insertAdjacentHTML` or `outerHTML`. Model output and pasted
  text are untrusted; build DOM with `createElement` and `textContent`.
- URLs are extensionless: `/guide`, `/mcp`, `/tools/report-check`. Never link to
  an `.html` file.
- One webfont, self-hosted: Archivo (`web/public/fonts/`, SIL Open Font
  License) for headings, labels and stamps. Running text and code use system
  font stacks. No font service, no other font file. The design system is in
  `DESIGN.md` and `web/site/COMPONENTS.md`.
- Edit pages in `web/site/pages/`, then regenerate. The HTML in `web/public/` is
  build output that is committed.

## Local development

Node 24 and Wrangler 4.

```bash
cd web
npm ci --ignore-scripts
node ../scripts/build-site.mjs
npx wrangler d1 migrations apply bounty-operator-accounts --local
npm run dev
```

Create `web/.dev.vars` first. The file is git-ignored.

```text
SITE_ORIGIN="http://localhost:8787"
BILLING_MODE="disabled"
IP_HASH_KEY="any-local-value"
```

Open `http://localhost:8787`. Passkeys work on `localhost`, and with
`BILLING_MODE="disabled"` no Stripe key is needed.

## Tests

```bash
cd web
node ../scripts/select-profiles.mjs --stub # the Worker reads hosted profiles from the stub
npm test                                   # node:test suites in web/tests
npm run smoke:stream                       # local workerd, in-memory D1 and a stand-in provider
npx --no-install tsc --noEmit              # Worker types
node ../scripts/build-site.mjs --check     # generated HTML matches the page sources
```

`--check` writes nothing and exits non-zero when a committed page differs from
what its source module generates. CI runs the same five commands.

`smoke:stream` builds the Worker without deploying it, then runs it in local
workerd with an in-memory database and a stand-in provider. It checks streamed
events, quota bookkeeping, disconnect cleanup and the hosted-output guard.
Cloudflare metadata fetching, telemetry and the banner's update check are disabled;
it needs no account,
provider key or production configuration. This checks the selected profile
source, which is the community stub in CI, not the private production method.

Two smoke scripts run against a local `wrangler dev` and refuse any other host:

```bash
node tests/auth-smoke.mjs http://localhost:8787
node tests/portal-smoke.mjs http://localhost:8787 <absolute-path-to-local-d1-sqlite>
```

`auth-smoke` covers registration, sign-in, CSRF, recovery rotation and cleanup.
`portal-smoke` covers account isolation, passkeys, connection tokens, quota and
the release of a reservation when a review fails. Neither contacts a model
provider or Stripe.

The MCP package has its own suite:

```bash
cd mcp
npm ci --ignore-scripts
npm test
node ../scripts/build-mcp.mjs --check      # the download under web/public/dl matches the package
```

Its parity tests load the Worker, so run `npm ci --ignore-scripts` in `web/`
first.

## HTTP API

Errors are JSON: `{ "error": string, "code"?: string }`. The codes a review
returns: `privacy_block` and `privacy_warn` (with `findings`), `daily_used`
(with `resetsAt`), `operator_only` (the `verdict` and `panel` profiles on an
account without Operator, refused before the provider is called),
`review_running`, `provider`, `output_withheld` and `reviews_paused`. MCP `prepare_review` returns `hosted_profile` for a hosted
profile.

| Route | Purpose |
| --- | --- |
| `GET /api/health` | Version, the state of billing, reviews and D1, and `profiles`: `hosted` or `community`. Returns 503 when D1 is down. |
| `GET /api/profiles` | The listed profiles: name, description, inputs, output section titles and `hosted`. |
| `GET /api/account` | Session state, usage, plan, limits and the CSRF token. |
| `POST /api/review` | Run a review. JSON, or server-sent events when `stream` is true. |
| `POST /api/client/review` | The same review for a `bok_` connection token. JSON only. |
| `GET /api/client/account` | Usage for a connection token. |
| `POST /api/mcp` | Stateless MCP over HTTP (JSON-RPC 2.0). |
| `POST /api/event` | Aggregate funnel counter. Whitelisted event names, no account id. |

Mutating account routes require the exact site origin and the session CSRF
token. Passkey removal, recovery rotation, connection creation and account
deletion require a sign-in within the last 10 minutes.

Quota is enforced in D1 with an atomic reservation. Free accounts run one review
at a time and complete one per UTC day. Operator accounts run four at a time
with no daily cap. A failed review releases its reservation.

## Configuration

`web/wrangler.jsonc` is the public template. Local development, the tests and
a fork's own deploy run from it. It names no account, no route and no live
database, billing is off, and its Worker is called `bounty-operator-dev`, so a
`wrangler deploy` run by mistake cannot replace the production Worker. Its
values: `SITE_ORIGIN`, `BILLING_MODE`, `STRIPE_PRICE_ID`,
`STRIPE_PORTAL_CONFIGURATION` and `AI_REVIEW_ENABLED`.

The production configuration is `web/wrangler.production.jsonc`. Git ignores
it: it holds the account, the routes, the database id and the Stripe ids.

Secrets are set with `wrangler secret put` and never committed:

| Secret | Used for |
| --- | --- |
| `STRIPE_SECRET_KEY` | Checkout, customer portal and subscription state |
| `STRIPE_WEBHOOK_SECRET` | Verifying signed webhook events |
| `IP_HASH_KEY` | HMAC key for rate-limit buckets, so raw IP addresses are never stored |

Paid access is granted from the signed webhook after the Worker re-reads the
subscription from Stripe. The checkout success URL alone grants nothing.

## Deploy

```bash
cd web
npx wrangler d1 migrations apply bounty-operator-accounts --remote --config wrangler.production.jsonc
npm run deploy
npm run verify:live -- --base-url https://bountyoperator.com --alias https://www.bountyoperator.com
```

Apply migrations before deploying the Worker that needs them.

`npm run deploy` is the production deploy (`scripts/deploy.mjs`). In order: it
refuses with one line when `wrangler.production.jsonc` is missing, selects the
hosted profiles and refuses the stub, runs the leak audit, checks that the
pages match their sources, then runs
`wrangler deploy --config wrangler.production.jsonc`. `npm run deploy:check`
runs the same gates and builds the production bundle without deploying it.

`npm run verify:live` reads a running site from the outside and exits 1 when a
check fails: `/api/health` (version, database, `"profiles": "hosted"`), the
security headers and the content security policy on `/` and `/guide`,
`security.txt`, `robots.txt` and the sitemap, every sitemap page (200, a
`<title>`, no script from another origin), the redirect from an alias host,
`/api/profiles` as metadata only, the MCP endpoint, and the checksum of the
served MCP package. It sends no secret.

`npm run lighthouse` measures the main pages of the live site with Lighthouse,
on a phone and on a desktop, and prints the four category scores, the lab
metrics and every audit that did not pass. It runs one pinned Lighthouse
release through `npx` on the Chrome installed on the machine, which needs
Node 22.19 or newer;
`npm run lighthouse -- --psi` measures through Google's PageSpeed Insights API
instead, with a key in `PAGESPEED_API_KEY`. `-- --all` covers every page of
the sitemap, `-- --min 90` exits 1 when a score is under 90, and
`-- --base-url http://localhost:8787` measures a local server.

A fork deploys its own Worker from the template: set a route or `workers_dev`,
its D1 database id and `SITE_ORIGIN` in `web/wrangler.jsonc`, then
`npx wrangler deploy`. Its `/api/health` reads `"profiles": "community"`;
check it with `npm run verify:live -- --base-url <origin> --profiles community`.

To pause hosted reviews without taking the site down, deploy with
`AI_REVIEW_ENABLED` set to `"false"`. Accounts, billing webhooks and
cancellation keep working.
